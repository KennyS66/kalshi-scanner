# Industry research: small-scale algo trading practices for short-duration binary markets

Date: 2026-08-02
Scope: research/writing only, no code changes. Written for the kalshi-scanner bot (single strategy on KXBTC15M, paper-primary, per-session 100-trade live gate, flat JSONL logs, nightly grid-search tuner + backtest_gate/replay harness, unused ETH/SOL/sports scanning infra).

---

## 1. Per-market/per-regime model separation

The pattern that shows up consistently across open-source multi-asset trading engines and the quant-architecture writeups is **strategy-as-plugin over a shared event/execution core**, not fully independent stacks per market and not one strategy with regime branches baked in.

- **NautilusTrader** (production-grade, Rust-core, Python-strategy, multi-venue) is the clearest reference implementation: a single event-driven message bus, portfolio/risk/execution engine, and data catalog are shared; each `Strategy` (subclass of `Actor`) is an isolated unit with its own state, instrument subscriptions, and parameters. Multiple strategies run inside one `TradingNode`/process when they're small and correlated risk needs to be seen centrally; each gets its own process when workload isolation or crash containment matters more than shared risk visibility. [Architecture](https://nautilustrader.io/docs/latest/concepts/architecture/), [Why NautilusTrader Exists](https://nautilustrader.io/blog/why-nautilustrader-exists/)
- The "modular quant system" writeups (Medium/Brenndoerfer-style architecture posts) describe the same split as **Model Creator / Model Manager / Ensemble Creator / Portfolio Construction**: individual per-instrument or per-signal models are versioned and trained independently, but they all feed a shared risk and portfolio layer rather than each having its own execution/risk stack. [Quant Trading Research Architecture](https://symeta.medium.com/inside-the-black-box-a-qhf-research-architecture-analysis-750d07914b08), [Modular Architecture](https://hiya31.medium.com/a-modular-architecture-for-systematic-quantitative-trading-systems-2a8d46463570)
- On ensembles vs. fully independent models: the trend cited across quant-blog sources (BuildAlpha, and general commentary) is toward **many small, independently-validated edges combined into an ensemble/vote** rather than one large model, specifically because it bounds overfitting per-component and lets each component be retired without touching the others. The tradeoff called out explicitly: ensemble/meta-learning overhead is a real cost at intraday/high-frequency cadence, so for fast-cycling strategies (which a 15-minute Kalshi market is) the sharing should be in *infrastructure* (data ingestion, execution, risk, logging) not in a heavyweight meta-model combining live signals across markets. [Ensemble Strategies](https://www.buildalpha.com/trading-ensemble-strategies/)

**Takeaway for "how much to share":** the isolation boundary that matters is *parameters and signal logic* (per-market, independently tunable, independently gated), not *infrastructure* (one execution path, one risk/kill-switch layer, one logging schema, one replay harness that all strategies run through). Building N fully separate bots per market is the anti-pattern every source implicitly warns against — it's what causes the "complexity exploding" problem the task description flags, because fixes to fill-simulation, gating, or logging then have to be replicated N times and drift (see §4).

## 2. Data management: when flat JSONL stops being enough

Concrete numbers from this repo make the question non-hypothetical: `data/whales/signal_feature_log.jsonl` is already **~294,000 lines**, growing daily, and is loaded into memory for replay/tuning per the task description.

- General consensus across multiple 2025-2026 DuckDB-vs-SQLite writeups: **SQLite becomes clearly worth it once you're doing real querying/filtering at roughly 100K+ rows**, or once you need concurrent readers, indexed lookups, or joins across log types (trades × features × outcomes) instead of full-file scans. Below that, flat files are fine. [DuckDB vs SQLite roundup](https://motherduck.com/learn/duckdb-vs-sqlite-databases/), general threshold discussion via search
- For the specific *analytical/backtest* workload (scan-heavy, aggregate-heavy, columnar filters like "all signals where regime=X and hour=Y"), **DuckDB is the more directly applicable upgrade, not SQLite** — 2025-2026 sources describe it as "the SQLite for analytics": it queries Parquet/CSV/JSON **in place with no ETL step**, uses columnar + vectorized execution, and is explicitly recommended for retail/small-firm backtesting because it's a single embedded file with no server. [DuckDB vs SQLite 2025](https://medium.com/@bhagyarana80/duckdb-vs-sqlite-the-2025-data-analysis-showdown-0f01711db50b), [DuckDB for traders](https://www.marketcalls.in/python/duckdb-tutorial-for-traders-a-python-guide.html), [DuckDB Tutorial](https://www.timestored.com/data/duckdb/duckcon-stock-data-analysis)
- Practical benefit that's concrete rather than hand-wavy: DuckDB **can query the JSONL files directly** (`read_json_auto`) without a migration step at all — meaning you can get faster, indexed, out-of-core replay queries without changing the write path or risking write-path drift, and only convert to Parquet later for compression once file size becomes the bottleneck rather than row count. Parquet's own 2025-2026 gains (2-37% smaller, 4-27% faster writes) matter once you're archiving rather than actively querying. [Parquet 2025-2026 improvements](https://dev.to/dataformathub/duckdb-arrow-and-parquet-the-ultimate-analytical-stack-for-2026-2mbi)
- The actual correctness benefit (not just speed) that's most relevant to a replay harness: **out-of-core, indexed query execution structurally prevents the load-everything-into-memory pattern from silently truncating or OOM-failing** as logs grow, and lets replay/tuner scripts filter by session/day/regime with a `WHERE` clause instead of hand-rolled Python filtering logic that has to be kept in sync with whatever the live bot's session-classification logic does.

**Takeaway:** the JSONL write path (append-only, crash-safe, human-diffable) is worth keeping as the source of truth — don't replace it. The upgrade is adding a **DuckDB read layer over the JSONL/Parquet files for replay and tuning**, which is close to a drop-in change (no ETL, same files) and buys indexed/out-of-core queries without touching how the live bot writes.

## 3. Binary/prediction-market-specific edge sources

This is the section with the most Kalshi-specific, non-generic material. Ordered roughly by how directly it transfers to a 15-minute BTC strike market.

### 3.1 Favorite-longshot bias — quantified, Kalshi-specific, and NOT yet tested here
"Makers and Takers: The Economics of the Kalshi Prediction Market" (Karl Whelan, working paper, 300,000+ Kalshi contracts) is the most directly relevant academic source found. Key findings from search-indexed summaries of the paper:
- Kalshi prices are informative and get **more accurate as markets approach closing** — consistent with what you'd expect from a 15-minute market that's mostly "priced in" by t-2min.
- There's a systematic **favorite-longshot bias**: contracts priced 5-20¢ (implying 5-20% probability) actually win only ~2-12% of the time; contracts priced 80-95¢ win ~96-98% of the time. I.e., longshots are *overpriced* and favorites are *underpriced* relative to realized frequency.
- The bias is explained by a **maker/taker asymmetry framework** — the theory predicts different bias patterns for the liquidity-providing side vs. the liquidity-taking side, which the data supports.
- The paper explicitly **does not analyze Kalshi's hourly-reset crypto/index markets** — it limits itself to markets open 24h+. That's a direct, citable gap: nobody has published the equivalent longshot-bias analysis for the 15m/hourly crypto contracts this bot trades. [Paper](https://www.karlwhelan.com/Papers/Kalshi.pdf), [CEPR summary](https://cepr.org/voxeu/columns/economics-kalshi-prediction-market)
- Separately, a Stanford Law School summary of an adverse-selection study using 41.6M Kalshi trades found that **traders systematically overbet YES in markets that settle NO**, and that this behavioral overbetting cross-subsidizes market-maker losses from informed order flow — a mechanism that's compatible with (arguably the same phenomenon as) the longshot bias above, from the maker's-book side rather than the price-bucket side. Also: one-sided order flow (VPIN-style toxicity) predicts maker losses in *single-name* markets but **not in broad-based markets** — worth checking whether BTC 15m (single-underlying, high-frequency) behaves more like the "single-name" or "broad-based" category in that framework. [Stanford Law summary](https://law.stanford.edu/2026/04/21/adverse-selection-in-prediction-markets-evidence-from-kalshi/)

This is distinct from the already-ruled-out "distance-to-strike filtering for fade entries" — that was an entry-timing filter tested against this bot's own signal log; the longshot-bias literature is a **pricing-level mispricing claim independent of entry timing** (i.e., "at a given implied probability, is the realized frequency systematically different"), which hasn't been tested against this bot's data yet as far as the provided context indicates.

### 3.2 Cross-exchange arbitrage — real but not viable at this bot's scale
Multiple sources (Frenzy Capital, a Fed working paper on Kalshi/Polymarket arbitrage, Quantpedia) converge on the same picture: **arbitrage between Kalshi and Polymarket for the same event is real and persistent for slow-resolving markets** (a Fed paper found mean arbitrage profit of 4.87% on Clarity Act markets, 89.1% of days exploitable; 1.38% mean profit on Fed rate-hike markets, 63.9% of days), but **for fast markets the window is seconds to low minutes** and disappears after transaction costs. [Fed working paper](https://www.federalreserve.gov/econres/feds/files/2026010pap.pdf), [Quantpedia](https://quantpedia.com/systematic-edges-in-prediction-markets/) — not practically actionable for a 15-minute BTC market without colocated low-latency infra, and Polymarket doesn't list the same BTC 15m contract structure as Kalshi anyway, so this is more a dead-end-to-note than an opportunity.

### 3.3 Whale/order-flow tracking — confirms the existing dead-end, adds a structural reason why
The task notes a whale-order-flow trend signal already failed validation. Current whale-tracking research (2025-2026 tooling writeups: Polywhaler, Rivo, Alphascope, and a Kalshi-specific "alpha research" gist) adds a structural explanation worth recording rather than re-testing: **Kalshi is not on-chain** (unlike Polymarket, which settles on Polygon and is fully visible), so real-time whale/large-order detection on Kalshi is inherently laggier and noisier than on Polymarket — tools explicitly describe Kalshi whale-tracking as "underdeveloped ... due to centralized architecture." Multiple sources also warn that by the time a whale alert is visible, price has typically already moved, and that whale signals can be spoofed (fake large orders to induce follow trades). This is consistent with — not contradictory to — the prior finding that the whale-order-flow signal failed train/test validation on this bot's own data. [Alphascope](https://www.alphascope.app/blog/polymarket-whale-tracking-order-flow), [Kalshi alpha research gist](https://gist.github.com/2080ufo/aece51137bf9dc278014552bbbd81f4e)

The same gist's "insider detection" idea (fresh wallets, <5 lifetime txns, making outsized trades relative to book depth, 1-4h before news) is **not applicable to BTC 15m markets** — it targets slow-resolving news-driven single-name markets where informed traders have a real information edge before public news; a 15-minute BTC strike has no analogous "insider" information source. Flagging this so it isn't mistakenly generalized.

### 3.4 0DTE-options gamma/pinning literature — directionally relevant, not a drop-in signal
0DTE-equity-options research (Dim/Eraker/Vilkov, and several dealer-gamma-exposure explainers) documents that **dealer gamma positioning measurably affects intraday price action**: positive dealer gamma dampens volatility and produces mean-reversion/pinning near strikes; negative dealer gamma amplifies moves. [0DTEs: Trading, Gamma Risk paper](https://papers.ssrn.com/sol3/Delivery.cfm/4692190.pdf?abstractid=4692190) This mechanism doesn't transfer directly — Kalshi 15m BTC markets have no dealer options-hedging flow underneath them, so there's no equivalent "gamma wall" — but the *general pattern* (systematic price behavior driven by identifiable structural flow near a specific level/strike, at short time horizons) is the closest analog in mainstream quant literature to what the ruled-out "distance-to-strike fade filtering" was trying to capture. Worth knowing this general mechanism is real in options markets, and that its absence in Kalshi's structure is itself informative about why the distance-to-strike test failed — there's no equivalent liquidity-provider hedging obligation creating pinning behavior on Kalshi.

### 3.5 Execution-realistic backtesting benchmark, Kalshi-specific
Found a directly relevant new artifact: **PredictionMarketBench** (Arora & Malpani, 2026) — a SWE-bench-style benchmark that does deterministic event-driven replay of real Kalshi orderbook/trade data (crypto, weather, sports episodes) with maker/taker semantics and fee modeling, specifically built to make backtest results execution-realistic. [Paper](https://www.catalyzex.com/paper/predictionmarketbench-a-swe-bench-style), [GitHub](https://github.com/Oddpool/PredictionMarketBench) — this is more relevant to §4 below (a working reference implementation of "how do you avoid backtest/live divergence on Kalshi specifically") than to finding new edge, but it also reports that **naive agents underperform primarily due to transaction costs and settlement losses**, and fee-aware strategies stay competitive mainly in volatile episodes — a useful sanity check that fee/edge modeling matters as much as directional signal quality.

## 4. Live-vs-paper drift risk

This repo has three separate scripts touching execution-adjacent logic: `bot_broker.py` (live), `backtest_gate.py` and `bot_replay.py` (replay/gate) — each independently implementing fill-related logic (`grep` for fill/slippage hits all three plus `swing_bot.py`/`web.py`). That's the exact shape of risk the industry sources warn about.

- The single most load-bearing pattern across every backtesting-pitfalls source: **backtests default to filling at the exact quoted price or next-bar open/close**, which "a historical bar tells you where price traded, but does not tell you whether your order would have been filled there, how much size was available before you, or how the book would have responded to your own participation." [Why Backtesting Environments Differ](https://algobulls.com/blog/algo-trading/backtesting-technical-factor)
- The recommended fix pattern, described as "zero-delta" architecture: **one codebase, same strategy/order-routing code runs unmodified in both backtest and live**, with only the venue adapter swapped (simulated fill engine vs. real exchange connection), and **every order passes through the same risk layer in both modes**. This is the architectural answer to "how do you stop drift" — not better documentation or more frequent audits, but structurally making it impossible for the two paths to diverge because they're the same code. [Event-driven backtesting](https://www.binaryfintech.com/en/blog/event-driven-backtesting/)
- NautilusTrader is the clearest existing implementation of this: same `Strategy`/`Actor` code runs against a backtest `ExecutionEngine` or a live one; the strategy layer is unaware which it's talking to. [NautilusTrader backtesting docs](https://nautilustrader.io/docs/latest/concepts/backtesting/)
- Event-driven (not vectorized) backtest architecture is also called out as structurally preventing look-ahead bias: because the simulation loop only ever has access to a priority queue of events up to timestamp *t*, "data from t+1 is not yet present in the system's memory," making a whole category of bugs impossible rather than merely policed. [Look-ahead bias prevention](https://inferensys.com/glossary/quantitative-finance-and-algorithmic-trading/backtesting-engine-architecture/look-ahead-bias)
- For fill realism specifically on order-book-quoted binary contracts: realistic simulation requires matching against sequential order-book depth per price level (not a single "last price"), modeling maker vs. taker fee asymmetry (Kalshi has real maker/taker fee structure), and treating slippage as a function of order size vs. available depth rather than a flat percentage. PredictionMarketBench (§3.5) is a concrete existing reference implementation of exactly this for Kalshi specifically.

**Practical translation for this repo:** the risk isn't hypothetical — having `bot_broker.py`'s live fill logic and `backtest_gate.py`/`bot_replay.py`'s simulated fill logic as separate implementations is precisely the pattern every source identifies as the drift mechanism. The fix isn't "test more," it's **extracting one fill/execution-simulation function that both the live broker and the replay/gate harness call**, so a fix to fill realism (which the task description says has already bitten this codebase once) can't be applied to one path and silently missed in the other.

## 5. Risk management for small live-money algo tests

- **Kill-switch triggers**, consistently described across retail-focused sources: daily loss limit, max drawdown limit, connectivity/heartbeat failure, and single-trade loss threshold — any breach halts new order submission (not necessarily flattening existing positions, which is a separate, more aggressive control). [Risk Management Strategies](https://www.luxalgo.com/blog/risk-management-strategies-for-algo-trading/), [7 Risk Management Strategies](https://nurp.com/algorithmic-trading-blog/7-risk-management-strategies-for-algorithmic-trading/)
- **Drawdown limits should be layered** (daily / weekly / monthly / all-time), with graduated response rather than binary on/off — reduce size first, then pause, then full shutdown, rather than jumping straight to a kill. [Reducing Drawdown](https://tradetron.tech/blog/reducing-drawdown-7-risk-management-techniques-for-algo-traders)
- **Staged rollout for individual traders**: every retail-focused source says the same thing — start with minimal capital, hard-code position size / daily loss / max-drawdown limits (not just monitor them), and treat these as circuit breakers baked into the code path rather than external dashboards someone has to watch. This matches this bot's existing per-session 100-trade + positive-net-avg gate structure — that gate *is* the staged-rollout mechanism; what's less clear from available sources is a standard "second stage" (e.g., a size-ramp after the first N live trades clear, rather than jumping from 1-contract to some other size). No source gave a specific universally-standard ramp schedule (e.g. "1 contract → 3 → 10"); this appears to be discretionary/firm-specific rather than a documented industry norm, so the existing 1-contract-sizing + per-session gate approach is reasonable and not obviously missing an industry-standard step.
- **Position sizing**: percentage-of-capital (typically 1-3% per trade) and volatility-based sizing are the two most commonly cited retail-appropriate methods; Kelly Criterion is mentioned but consistently with a fractional-Kelly caveat (full Kelly is considered too aggressive for live deployment given real-world edge-estimate uncertainty). [Turning Trading Concepts Into Automated Strategies](https://www.luxalgo.com/blog/turning-trading-concepts-into-automated-strategies-2/)
- On calibration as a *live-readiness* gate rather than just a backtest metric: one source suggests tracking realized Brier score over 100+ live/paper trades as a real-time check that probability estimates (not just P&L) remain well-calibrated — Brier < 0.20 as a rough "well-calibrated" bar, with human superforecasters in the 0.15-0.20 range and prediction-market wisdom-of-crowds in 0.12-0.18. This is a complementary metric to the existing "100 settled trades + positive net avg" gate — net avg P&L can be positive by variance even with poor calibration, whereas Brier score directly measures whether the model's implied confidence matches realized outcomes, which is arguably a more sample-efficient measure of calibration than P&L is. [Kelly/EV/Brier reference](https://poly-sim.com/wiki/probability-odds-explained.html)

## 6. Specific recommendations for this bot

1. **Extract one shared fill/execution-simulation function** used by both `bot_broker.py` (live) and `backtest_gate.py`/`bot_replay.py` (replay). This is the single highest-leverage change from all five research areas — it directly targets the fill-price-realism drift this codebase has already been bitten by, and every industry source treats "shared code path" as the standard fix, not "audit more carefully."

2. **Add a DuckDB read layer over the existing JSONL logs for `bot_tuner.py`/`bot_replay.py`**, without changing the write path. `signal_feature_log.jsonl` is at ~294K lines already, past the point (~100K rows) where multiple sources say full-file-scan-into-memory becomes a real cost/correctness risk. DuckDB can query JSONL in place (`read_json_auto`) — no migration, no ETL, and it removes the risk of replay/tuner scripts silently diverging in how they filter by session/day since it's one `WHERE` clause instead of duplicated Python filtering logic.

3. **Test the Kalshi-specific favorite-longshot bias (Whelan et al., "Makers and Takers") against this bot's own signal log**, bucketed by implied probability (price) rather than by distance-to-strike or entry-time-segment (both already ruled out). This is a different axis than what's been tested — it's a pricing-level claim ("at implied probability X, actual frequency is Y"), not an entry-timing filter — and the paper's authors explicitly did not test Kalshi's hourly/crypto markets, so this is a genuine untested gap rather than a re-tread.

4. **Treat the ruled-out whale-order-flow signal as structurally explained, not just empirically failed**: Kalshi's off-chain architecture makes real-time whale detection inherently laggier than on Polymarket (multiple 2025-2026 tools explicitly call this out), and by the time any whale signal is visible price has typically moved. Don't re-attempt whale-flow variants on Kalshi without solving the underlying visibility-lag problem first — this reinforces rather than contradicts the existing dead-end finding.

5. **For the "per-market model separation" goal**: when wiring in the currently-unused ETH/SOL/sports scanning infra, follow the strategy-plugin-over-shared-core pattern rather than building parallel bot stacks. Concretely: keep one execution/risk/kill-switch/logging path (item 1 above generalizes to this too), one replay/tuner harness that all strategies run through, but let each market/strategy have independently-tunable parameters and its own instance of the existing per-session live-gate. This avoids the "N complete copies to maintain" failure mode multiple architecture sources warn about, while still giving each market's model independent tuning and independent go/no-go gating — matching the existing per-session gate design, just extended per-market.

6. **Layer the drawdown response instead of binary live/paused**: current per-session gate is a good entry gate, but consider a graduated *live* circuit breaker once a session goes live — e.g., reduce size or auto-pause a specific session on a daily-loss or rolling-drawdown breach, rather than relying solely on manual pause. This is consistent with the existing per-session live/pause control shipped 2026-08-02, just adding an automatic trigger rather than requiring a manual check.

7. **Track realized Brier score as a secondary live-readiness signal alongside the existing 100-trade + positive-net-avg gate.** Net average P&L can be positive by variance with poorly-calibrated probability estimates; Brier score is a more direct, more sample-efficient measure of whether the model's confidence matches reality, and is cheap to compute from the same trade log.

8. **If ETH/SOL/sports strategies are ever tuned independently, budget for ensemble/infra overhead deliberately** — sources are consistent that many-small-edges-combined beats one big model for overfitting reasons, but also that ensemble/meta-learning overhead is a real cost at intraday cadence. For a 15-minute-cycle strategy, keep the "ensemble" at the infrastructure level (shared execution/logging/gating) rather than building a live cross-market meta-model, which would add latency and complexity disproportionate to a 15-minute decision window.

9. **Consider PredictionMarketBench (Oddpool, github.com/Oddpool/PredictionMarketBench) as a reference implementation**, not necessarily a dependency to adopt — it's a Kalshi-specific, maker/taker-fee-aware, orderbook-realistic replay framework built by someone solving exactly the fill-realism/drift problem in item 1. Worth reading its execution-simulation code even if not integrating it directly, since it's a working example of the "shared, execution-realistic simulator" pattern for this exact exchange.

10. **Low-priority/no-action**: cross-exchange (Kalshi/Polymarket) arbitrage is real per the Fed working paper cited in §3.2, but only for slow-resolving markets (days), not the 15-minute BTC contracts this bot trades — the arb window on fast markets is seconds-to-minutes and Polymarket doesn't offer an equivalent contract structure. Not worth building toward.
